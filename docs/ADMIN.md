# Administrator operations

The admin portal is deployed separately from the public Flutter app and has no public navigation link. Search indexing is disabled. The URL can still be discovered; verified server authorization is the security boundary.

The first owner email was provisioned privately from the human user’s answer. Register that email, verify its email link, sign in and enroll an authenticator. Every management request requires the approved email, a live Supabase session and AAL2. User metadata cannot grant access. An administrator may approve additional emails; all approved administrators have full business-management privileges and must verify email and MFA. Self-revocation and deletion of administrator accounts through the user-deletion control are blocked. Keep authenticator backups; recovery requires trusted operator intervention if all factors are lost.

Controls include prompt/image create and edit, drafts, publish/archive/delete, free/Pro text, featured discovery placement, categories including custom categories, future daily inventory, community approval/rejection, user lists and permanent account deletion, promotional Pro grants and revocation, administrator access, home announcements and an activity log. User deletion removes owned remix files before deleting the Auth account and cascading app rows. It does not cancel external store subscriptions. Vendor credentials, billing products, DNS and infrastructure remain managed in their respective service dashboards.

Image uploads accept JPEG, PNG or WebP up to 20 MB / 25 megapixels. A fresh canvas resizes the longest side to 1600 px, removes metadata and encodes a JPEG, reducing quality if needed to stay below 2 MB. The Edge Function checks image bounds/signature/size and computes SHA-256. The compressed bytes are stored in the private `catalog-media` Storage bucket. Related title, full prompt, category, model, variables, attribution, tags, flags, status, version and image path/hash are stored in `private.admin_catalog`. Database uniqueness rejects repeated normalized prompt text and byte-identical uploaded images. This is exact-content deduplication, not semantic/perceptual similarity detection.

Published catalog data is returned by `catalog-content`; paid full text and draft/archived content are excluded. Published uploaded images receive seven-day viewing URLs. Updates appear after a successful app sync; offline caches and previously issued image links are not remotely erased immediately. Images are preview references unless the administrator verifies that they are actual outputs. Media cleanup is attempted after replacement/deletion; the API reports a cleanup warning if storage is unavailable. Backups must cover both private database records and Storage objects.

The 33 original catalog records have been imported into the managed database. New installs retain the bundled fallback; online synchronization uses the managed catalog. Static external-source publication remains separate from curated administration. `node tools/bootstrap_admin.mjs` downloads the pinned, SHA-256-checked Supabase browser SDK before deploying the `admin/` directory. The portal only contains the public URL and publishable key; no service-role secret belongs there. Authentication redirect origins include the admin portal.

Validation includes SQL isolation tests, real password + authenticator verification, browser image compression and private draft saving, publication and successful signed-image delivery. A disposable original PNG compressed from approximately 30 KB to 3.3 KB JPEG. Additional API lifecycle checks are recorded in the release audit.

Supabase advisor notes: the two public authenticated SECURITY DEFINER RPCs are intentional guarded entry points with fixed empty search_path, live-session checks and MFA. The tests prove ordinary users cannot use them. Leaked-password protection is currently disabled at the Auth service; enable it when available on the project plan. New index unused notices do not establish a performance defect on a freshly populated catalog.
